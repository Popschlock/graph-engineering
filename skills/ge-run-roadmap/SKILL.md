# /ge-run-roadmap <r> [once | dry | --until <id>]

You are the orchestrator. You hold almost nothing: the briefs you dispatch and two short reports per task. Every read is one of the `GE` commands below, run from the project root (the directory holding `ge/`); you never open a log, a suite's output, a source file or a whole doc into your context. The work happens in fresh subagents whose definitions carry their model and effort (`graph-engineering:ge-task` opus xhigh, `graph-engineering:ge-reader` fable high, `graph-engineering:ge-verifier` opus xhigh, `graph-engineering:ge-reviewer` fable high). Dispatch every one of them by its namespaced name; if the Agent tool does not know the namespaced name, use the bare `ge-task` (and the same for the other three). If the project's `ge/config.md` `## Tiers` names a different model for a role, pass it as the Agent call's `model` — that per-dispatch argument is the tier override.

`GE` = `python "${CLAUDE_PLUGIN_ROOT}/scripts/ge.py"`. `<session>` = the 8 characters after `session_` in this session's Claude-Session link. Arguments: none = loop until a stop; `once` = one dispatch round and its closes, then stop; `dry` = print every brief you would dispatch and stop; `--until <id>` = stop when `<id>` closes or is blocked. `<r>` must appear in `GE list`; otherwise say so and stop.

Several tasks run at once. The roadmap's `locks` column says what each task holds while it runs, and `GE dispatchable` only ever names tasks whose locks share nothing with the tasks already running, so you never have to reason about which tasks may overlap: the files do. The subagents work in the same tree at the same time and commit through `GE commit`, which serialises them.

## The loop

1. **Guards** — `GE guards <r>`. It prints `stop:`, `pause:`, one `lanes:` line (how many tasks are in progress and the locks they hold), one `tree:` line (`clean`, `DIRTY` or `UNKNOWN (...)`) and one line per configured guard (`ok`, `BLOCKED` or `ERROR ...`).
   - `stop: PRESENT` → say "stopped by ge/<r>/STOP" and stop. Tasks already running finish on their own; do not dispatch more.
   - `pause: <reason> | <note>` → act on the reason (below), then `ScheduleWakeup` 1800 s (`noop: true`, reason "paused"); on wake run step 1 again.
   - `guard <name>: BLOCKED` → say which, `ScheduleWakeup` 1800 s (`noop: true`, reason "guard <name>"), re-check on wake. Never run or close anything to clear it.
   - `tree: UNKNOWN (...)` or `guard <name>: ERROR ...` → the check could not run, so it fails closed: treat it exactly like `guard <name>: BLOCKED` — say which, `ScheduleWakeup` 1800 s (`noop: true`, reason "guard <name>"), re-check on wake. Never dispatch on one.
   - `tree: DIRTY` → continue. With lanes running it is a peer's work in flight; with none it is a cut-off session, and the rules tell the task agent what to do.
2. **Dispatchable** — `GE dispatchable <r>`, which prints one `<id> | <subject> | <gate names> | <locks>` line per task that can start now, up to `max parallel` from `ge/config.md` minus the tasks already running, or `none`. Every task already running is on stderr as `running: <id> (<session>) holds <locks>`; those are your lanes, not errors. `none` with no lanes running → say "nothing ready" plus the `blocked:` lines it printed, and stop. `none` with lanes running → wait for a notification (step 5).
3. **Briefs** — for each line, `GE brief <r> <id>`; keep stdout and the exit code. Exit 2 → no kickoff named `<id>` and `GE` printed a minimal brief from the row: use it and, unless `dry`, record `GE event <r> revised "no kickoff for <id>; minimal brief from its spec"`. `dry` → print every brief and stop.
4. **Dispatch** — `GE start <r> <id> <session>` for each. Exit 1 means its locks collide with a task that started since you asked; skip it this round. Then ONE message holding every `Agent` call, one per started task: `subagent_type` `graph-engineering:ge-task`, or `graph-engineering:ge-reader` when the subject starts with `READ:`. Each prompt is that task's brief verbatim plus two lines: `Your session link for the commit footer: <this session's Claude-Session URL>; your session id is <session>.`. Say `dispatched: <ids>`. Then wait; do nothing meanwhile (no polling, no reading).
   - Each report that comes back is exactly: `commit: <hash>`; one `gate <name>: <captures>` line per gate (or `gates: none owed`); then one of `closed: <id>` | `blocked: human call` | `blocked: guard <name>` | `blocked: guard tree` | `stopped`; then `unlocked: <ids or none>`. `ge-reader` reports the same shape, with `summary: <path>` as a third alternative on the third line and `commit: none` for a summary.
5. **On each notification** — one task's report has arrived while the others may still be running. In ONE message do both of these: (a) act on the report as below, which for `closed:` means dispatching its verifier; (b) `GE dispatchable <r>` again, and dispatch whatever it now names exactly as in steps 3 and 4 (the close may have unlocked tasks, and a lane has freed). Then wait again.
   - `closed: <id>` (or `summary:` with a `commit:` hash) → `Agent` `graph-engineering:ge-verifier`; the prompt is exactly five lines: `roadmap: <r>`, `task: <id>`, `commit: <the hash from the task's report>`, `gates: <the gate names from the dispatchable line>`, `ge: python "${CLAUDE_PLUGIN_ROOT}/scripts/ge.py"`. Never forward the task agent's report.
   - `blocked: human call` (or any other `blocked: <why>` not listed) → the agent already wrote the files; continue. `blocked: guard <name>` / `blocked: guard tree` → step 1's wait once the running lanes have reported. `stopped` → dispatch nothing more and stop when the lanes have reported. `summary: <path>` without a hash → continue.
   - `VERDICT: PASS` → `GE close <r> <id> <hash> "<the captures after 'gates: ' on the verifier's gates line>" --session <session>` — the `<name>=<captures>` tokens only, never the words `gates:`, so the ledger's outcome starts with them and the next verifier can read them back (a no-op when the agent already closed it: nothing is written, not even a re-render). Count the close; say the close line.
   - `VERDICT: MISS` → `GE event <r> miss "<the first miss line>" --session <session>` first, so the ledger carries the miss whatever happens next. If that first miss line names another task's id, a lock, the editor, a build, or a file this task's spec does not name, the tasks interfered: `GE collide <r> <id> <the other id, or the lock name>`, so the retry runs alone. Then `GE start <r> <id> <session>` (if it exits 1, wait for the lanes it names to report, then start it) and re-dispatch `graph-engineering:ge-task` ONCE with the brief plus `The verifier found:`, the misses verbatim, and `Fix exactly those, re-run the gates they name, change nothing else, and close again.` Verify again. A second MISS → `GE block <r> <id> "<the first miss line>" --session <session>`, then `GE commit <r> <id> --close -m "ge(<r>): block <id> after two verifier misses"`; continue.
6. **Review** — after every N closes (`review every` in `ge/config.md`; 3 when absent; after a compaction, count the closes since the last `review` row in `GE ledger <r> 20` rather than remembering): `Agent` `graph-engineering:ge-reviewer` with `review roadmap <r> now; ge: python "${CLAUDE_PLUGIN_ROOT}/scripts/ge.py"`. Apply its answer — `moves: none`, `locks: none`, `reruns: none` and `calls: none` are sentinels, so apply nothing for a line that reads `none` and never write a node called `none`; an all-`none` proposal still runs the `GE event`, the `GE render` and the commit below. Otherwise each `moves` line is `X deps=<ids> — <reason>`, so first read `GE node <r> X` and keep its current `deps:` line, then `GE set <r> X --deps "<list>"` where the list is what follows `deps=` up to the em dash (` — `), trimmed — the reason is never part of `--deps`; each `locks` line is `X locks=<names> — <reason>` → `GE set <r> X --locks "<names>"` the same way; each rerun id → `GE set <r> <id> --status open`; each `calls` line → append `* <line>` under `## Open` in `ge/<r>/calls.md`. Then `GE validate <r>` (exit 2 → restore each moved node with `GE set <r> X --deps "<the ids after 'deps: ' on the kept line>"`, and say so); `GE event <r> review "<the REVIEW line>; next <its next ids>"`; `GE render <r>`; `GE commit <r> review --close -m "ge(<r>): review — <no change|reorder>"`.
7. **Loop** to step 2 unless `once` (after the round's lanes have all reported), or `--until <id>` just closed or was blocked.

## Pause reasons (step 1)

- `human-test` — print what to test: `GE ledger <r> 3`, each row's node subject from `GE node <r> <id>`, the path `ge/<r>/status.html`, and "resume with /ge-resume-roadmap <r>". Then wait.
- `summary <topic>` — if `ge/<r>/summaries/` has no `<today>-<topic>.md`: `Agent` `graph-engineering:ge-reader` with `Write the pause summary for roadmap <r>, topic: <topic>; ge: python "${CLAUDE_PLUGIN_ROOT}/scripts/ge.py"`; show its path and first paragraph. Then hold as `human-test`.
- `adjust` — the human is present (they paused): run the `ge-revise-roadmap` skill for `<r>`; when it closes, hold as `human-test` until resume.

## Rate limits and compaction

A subagent that returns a limit or credential failure (its report says so, or the notification is an error) → `ScheduleWakeup` 3600 s (`noop: true`, reason "usage window") and retry the same step on wake; three consecutive → stop and say so. After a compaction: run step 1 again; the `lanes:` line and `GE dispatchable` say where the run is, and the notifications of agents still running arrive as before. Do not try to remember what the reports said. `GE next <r>` still exists for a single-lane run; any `in progress:` line it prints on stderr is a running lane, not a stranded node, unless `lanes:` says nothing is in progress.

## What you say

`dispatched: <ids>` per round and one line per close: `<id> PASS <hash> — <the captures>`, the same string you gave the ledger: the captures after `gates: ` on the verifier's gates line. One line at a stop and why. Nothing else; the files carry the rest. The human can Ctrl-C at any time and `/ge-run-roadmap <r>` later.
