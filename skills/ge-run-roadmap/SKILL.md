description: Run a roadmap unattended from one interactive session. Each ready task goes to a fresh worker subagent, each finished task is checked by a fresh verifier subagent, a reviewer looks at the whole roadmap every few tasks, and the loop stops on a pause, a stop, or when nothing is ready. Use when the user types /ge-run-roadmap <r> [once|dry|--until <id>].

# /ge-run-roadmap <r> [once | dry | --until <id>]

You are the orchestrator. You hold almost nothing: one brief and two short reports per node. Every read is one of the `GE` commands below, run from the project root (the directory holding `ge/`); you never open a log, a suite's output, a source file or a whole doc into your context. The work happens in fresh subagents whose definitions carry their model and effort (`graph-engineering:ge-task` opus xhigh, `graph-engineering:ge-reader` fable high, `graph-engineering:ge-verifier` opus xhigh, `graph-engineering:ge-reviewer` fable high). Dispatch every one of them by its namespaced name; if the Agent tool does not know the namespaced name, use the bare `ge-task` (and the same for the other three). If the project's `ge/config.md` `## Tiers` names a different model for a role, pass it as the Agent call's `model` — that per-dispatch argument is the tier override.

`GE` = `python "${CLAUDE_PLUGIN_ROOT}/scripts/ge.py"`. `<session>` = the 8 characters after `session_` in this session's Claude-Session link. Arguments: none = loop until a stop; `once` = one node then stop; `dry` = print the brief you would dispatch and stop; `--until <id>` = stop when `<id>` closes or is blocked. `<r>` must appear in `GE list`; otherwise say so and stop.

## The loop

1. **Guards** — `GE guards <r>`. It prints `stop:`, `pause:`, one `tree:` line (`clean`, `DIRTY` or `UNKNOWN (...)`) and one line per configured guard (`ok`, `BLOCKED` or `ERROR ...`).
   - `stop: PRESENT` → say "stopped by ge/<r>/STOP" and stop.
   - `pause: <reason> | <note>` → act on the reason (below), then `ScheduleWakeup` 1800 s (`noop: true`, reason "paused"); on wake run step 1 again.
   - `guard <name>: BLOCKED` → say which, `ScheduleWakeup` 1800 s (`noop: true`, reason "guard <name>"), re-check on wake. Never run or close anything to clear it.
   - `tree: UNKNOWN (...)` or `guard <name>: ERROR ...` → the check could not run, so it fails closed: treat it exactly like `guard <name>: BLOCKED` — say which, `ScheduleWakeup` 1800 s (`noop: true`, reason "guard <name>"), re-check on wake. Never dispatch on one.
   - `tree: DIRTY` → continue; the rules tell the task agent what to do.
2. **Next** — `GE next <r>`, which prints `<id> | <subject> | <gate names>` on stdout. `none` → say "nothing ready" plus the `blocked:` lines it printed, and stop. Keep the id (the first pipe-separated field), the subject (the second) and the gate names (the third). If `GE next` printed any `in progress: <id> — in progress (<session>)` line on stderr, say `stranded: <id> (<session>)` once and continue — a node a dead session left marked is not yours to clear.
3. **Brief** — `GE brief <r>`; keep stdout and the exit code. Exit 2 → the last close mis-wrote `next.md` and `GE` printed a minimal brief from the row: use it and, unless `dry`, record `GE event <r> revised "next.md did not name <id>; minimal brief from its spec"`. `dry` → print the brief and stop.
4. **Dispatch** — `GE start <r> <id> <session>`. Then the `Agent` tool, `subagent_type` `graph-engineering:ge-task`, or `graph-engineering:ge-reader` when the subject starts with `READ:`. The prompt is the brief verbatim plus two lines: `Your session link for the commit footer: <this session's Claude-Session URL>; your session id is <session>.`. Wait for the notification; do nothing meanwhile (no polling, no reading).
   - The report that comes back is exactly: `commit: <hash>`; one `gate <name>: <captures>` line per gate (or `gates: none owed`); then one of `closed: <id>` | `blocked: human call` | `blocked: guard <name>` | `blocked: guard tree` | `stopped`; then `next: <id or none>`. `ge-reader` reports the same four lines, with `summary: <path>` as a third alternative on the third and `commit: none` for a summary.
5. **Verify** — If the report's outcome line (the line after the `commit:` and `gate`/`gates:` lines: `closed:` | `blocked: ...` | `stopped` | `summary:`) is not `closed: <id>`, skip the verifier: `blocked: human call` (or any other `blocked: <why>` not listed) → the agent already wrote the files, continue at step 7; `blocked: guard <name>` / `blocked: guard tree` → step 1's wait; `stopped` → stop; `summary: <path>` → treat it like `closed:` for this decision only if a `commit:` hash is present, otherwise continue at step 1. Only a `closed:` report — or a `summary:` carrying a hash — dispatches the verifier. Then `Agent` `graph-engineering:ge-verifier`; the prompt is exactly five lines: `roadmap: <r>`, `task: <id>`, `commit: <the hash from the task's report>` (its `commit:` line), `gates: <the gate names from step 2>` (`next`'s third field), `ge: python "${CLAUDE_PLUGIN_ROOT}/scripts/ge.py"`. Never forward the task agent's report. Wait.
   - `VERDICT: PASS` → `GE close <r> <id> <hash> "<the captures after 'gates: ' on the verifier's gates line>" --session <session>` — the `<name>=<captures>` tokens only, never the words `gates:`, so the ledger's outcome starts with them and the next verifier can read them back (a no-op when the agent already closed it: nothing is written, not even a re-render). Count the close; say the close line.
   - `VERDICT: MISS` → `GE event <r> miss "<the first miss line>" --session <session>` first, so the ledger carries the miss whatever happens next; then `GE start <r> <id> <session>` again (the fix pass is in progress too, and the page shows it), and re-dispatch `graph-engineering:ge-task` ONCE with the brief plus `The verifier found:`, the misses verbatim, and `Fix exactly those, re-run the gates they name, change nothing else, and close again.` Verify again. A second MISS → `GE block <r> <id> "<the first miss line>" --session <session>`, then `git add ge && git commit -m "ge(<r>): block <id> after two verifier misses"`; continue at step 7.
6. **Review** — after every N closes (`review every` in `ge/config.md`; 3 when absent; after a compaction, count the closes since the last `review` row in `GE ledger <r> 20` rather than remembering): `Agent` `graph-engineering:ge-reviewer` with `review roadmap <r> now; ge: python "${CLAUDE_PLUGIN_ROOT}/scripts/ge.py"`. Apply its answer — `moves: none`, `reruns: none` and `calls: none` are sentinels, so apply nothing for a line that reads `none` and never write a node called `none`; an all-`none` proposal still runs the `GE event`, the `GE render` and the commit below. Otherwise each `moves` line is `X deps=<ids> — <reason>`, so first read `GE node <r> X` and keep its current `deps:` line, then `GE set <r> X --deps "<list>"` where the list is what follows `deps=` up to the em dash (` — `), trimmed — the reason is never part of `--deps`; each rerun id → `GE set <r> <id> --status open`; each `calls` line → append `* <line>` under `## Open` in `ge/<r>/calls.md`. Then `GE validate <r>` (exit 2 → restore each moved node with `GE set <r> X --deps "<the ids after 'deps: ' on the kept line>"`, and say so); `GE event <r> review "<the REVIEW line>; next <its next id>"`; `GE render <r>`; `git add ge && git commit -m "ge(<r>): review — <no change|reorder>"`.
7. **Loop** to step 1 unless `once`, or `--until <id>` just closed or was blocked.

## Pause reasons (step 1)

- `human-test` — print what to test: `GE ledger <r> 3`, each row's node subject from `GE node <r> <id>`, the path `ge/<r>/status.html`, and "resume with /ge-resume-roadmap <r>". Then wait.
- `summary <topic>` — if `ge/<r>/summaries/` has no `<today>-<topic>.md`: `Agent` `graph-engineering:ge-reader` with `Write the pause summary for roadmap <r>, topic: <topic>; ge: python "${CLAUDE_PLUGIN_ROOT}/scripts/ge.py"`; show its path and first paragraph. Then hold as `human-test`.
- `adjust` — the human is present (they paused): run the `ge-revise-roadmap` skill for `<r>`; when it closes, hold as `human-test` until resume.

## Rate limits and compaction

A subagent that returns a limit or credential failure (its report says so, or the notification is an error) → `ScheduleWakeup` 3600 s (`noop: true`, reason "usage window") and retry the same step on wake; three consecutive → stop and say so. After a compaction: run step 1 again; the files say where the run is. Do not try to remember what the reports said.

## What you say

One line per close: `<id> PASS <hash> — <the captures>`, the same string you gave the ledger: the captures after `gates: ` on the verifier's gates line. One line at a stop and why. Nothing else; the files carry the rest. The human can Ctrl-C at any time and `/ge-run-roadmap <r>` later.
